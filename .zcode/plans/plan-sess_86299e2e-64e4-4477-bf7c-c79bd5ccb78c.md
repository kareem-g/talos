# Convert the AgentDeck mobile client to React Native (Expo) + local-notification system

## Confirmed decisions
- **Toolchain:** Expo (prebuild). Local notifications only — no APNs, no Apple account, no third-party push, per spec.
- **Web dashboard stays** for desktop (daemon keeps serving it). The RN app is the new mobile client in a new `mobile/` package; the Capacitor mobile shell is retired.
- **Target:** full mobile UI parity, executed in phases (acknowledged: many iterations; "done" = everything).

## Hard constraints (stated honestly)
- **Linux host:** I cannot compile/run iOS locally. The iOS IPA is built in CI (macos runner). I validate JS/jest/tsc locally and run the app on the **Android emulator** available here; final iOS verification is in CI / on a Mac.
- **iOS limitation (unchanged by RN, as your spec notes):** local notifications fire only while JS runs (foreground, or briefly backgrounded before iOS suspends the webview/JSC and kills the socket). Suspended/terminated ⇒ no delivery without APNs. We degrade gracefully and document this; no background-execution hacks, no false "guaranteed background" claims.

Used for reconnect sync. (Per-session pending already exists via `GET /api/mobile/sessions/{id}`.)

## Notification system (spec → real backend contracts)
- **Triggers** from existing mobile WS frames: `AgentEvent kind=permission_required` (approval; key = `payload.id`), `question_started` (action), `agent_completed` (finished), `agent_error` / `StateChange state=error` (errored). Wording mirrors backend `summarize_event` (prefer `payload.tool_name`/`prompt`). A single mapper keeps it **extensible** (auth-required, conflict, waiting-for-input slot in without hard-coding one type).
- **Delivery:** expo-notifications local notification; a category "View" action that **routes only** (never resolves).
- **Dedup:** persisted Set (MMKV) of notified request_ids/event_ids; skip repeats; survives reconnect (replayed frames are already deduped by `event_id` in `events.ts` `seenEvents`, plus the notified-set).
- **Tap handling:** response listener → extract `{sessionId, approvalId}` → navigate to Session → open the pending approval. The approval screen **re-fetches state** from `GET /api/mobile/sessions/{id}` (backend = source of truth); resolution happens only via the existing WS `Command{action:"approval_response"}` / `QuestionAnswer` after the user presses Approve/Deny. **Tapping never approves.**
- **Reconnect sync:** on connect/reconnect, `GET /api/mobile/pending`; notify each pending not in the notified-set; add to set. Catches approvals that arrived while disconnected.
- **Lifecycle:** foreground with the relevant approval already on screen → update UI, suppress the notification (no spam); foreground elsewhere / background-with-live-socket → notify; suspended/terminated → documented gap.
- **Permissions:** request on first relevant use with a why-explainer; on denial the app works normally, shows an in-app "notifications disabled" indicator + a button to open iOS Settings; never blocks agent usage.

## Phased build (to full parity)
- **A — Foundations:** revert ntfy; scaffold `mobile/`; Metro/tsconfig alias to dashboard pure modules; NativeWind + theme tokens (port the pure accent math) + fonts; port the adapter modules; backend `GET /api/mobile/pending` + tests.
- **B — Notifications:** expo-notifications module (permission, channel/category, show, MMKV dedup, tap routing); wire to WS frames + reconnect sync + lifecycle; in-app notification settings/indicator; **jest tests for all 12 spec scenarios**.
- **C — Navigation + core screens:** React Navigation (Pairing/Home/Session + drawer) with linking (pairing deep link, notification-tap route); Pairing (expo-camera QR + manual paste + verify + Keychain token); Home/Station (port `StationHome` + `homeView`: triage timeline, active list, workspace groups, attention rows, quick-launch); Session detail (`Timeline` + `StateZone` approval/question/resume/failure cards + working `Composer` + controls sheet); interactive approval/question cards resolving via WS.

- **E — Build/CI/retire Capacitor:** CI workflow building the RN iOS IPA (`expo prebuild` → `xcodebuild archive` unsigned → artifact) on a macos runner + an Android build; app icon/splash; Info.plist (ATS for the http daemon, camera + local-network usage); bundle id; retire `ios-capacitor.yml` + Capacitor deps/config + mobile-web-only paths (web dashboard stays for desktop).
- **F — Validation:** jest (ported events/sessionState/queue suites + the new notification suite), tsc, eslint; run on the Android emulator locally (boot → pair → WS connect → receive events → fire local notification → tap routes → reconnect sync → permission-denied path); iOS IPA via CI.

## Deliverables (your 9 items, produced at the end)
1) files changed; 2) new deps; 3) iOS config (Info.plist ATS/camera/local-network, bundle id, icon/splash, notification usage); 4) backend changes (`GET /api/mobile/pending`); 5) event types (reuse `permission_required`/`question_started`/`agent_completed`/`agent_error` — no new wire types); 6) dedup (MMKV notified-set keyed by request_id/event_id); 7) tap routing (response listener → session+approval, state re-fetched from backend); 8) reconnect sync (`/api/mobile/pending` diff → notify new); 9) the iOS suspended/terminated limitation, documented.

## Risks
- **Scale:** full parity is many thousands of lines across 60+ components and will span many iterations. I execute phase-by-phase, keeping the app runnable at each boundary, validating on Android locally + iOS in CI.
- `chat.tsx` (1,719 lines) + `Composer.tsx` (1,242) are the largest risks (XL) — phased within C/D so a usable app exists before they're complete.
- **No desktop-web regression:** the web app is untouched; shared modules are imported read-only.
- The notification outcome is bounded by iOS itself: this delivers reliable foreground/recent-background alerts with correct routing, dedup, and reconnect sync, but cannot page a fully-suspended app — an Apple platform constraint, not an implementation gap.
